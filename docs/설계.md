## 1. 무엇을 만드는가

자기소개서에서 "AI 활용 능력"을 보여 주는 포트폴리오다. 특정 회사에 맞추지 않고 여러 자소서에 돌려 쓴다.

**핵심 이야기 한 줄**

> 수업 실험에서 "피팅 구간에 따라 값이 달라진다"는 의문이 남아 AI와 분석 도구를 만들었고, AI가 낸 결과를 원자료로 다시 따져 사람이 직접 확인해야 할 것을 N개 항목의 검수 기준표로 정리했다.

- 대표 산출물은 **검수 기준표**다. 도구(코드)는 그 증거다.
- N은 미리 정하지 않는다. 아래 세 가지가 모두 붙은 항목만 남기고 그 수가 N이다.
  1. 사례: 무엇이 틀렸거나 틀려 보였는지
  2. 다시 계산하는 명령: 원자료에서 그 숫자가 나오는 명령 한 줄과 출력
  3. 직접 확인한 기록: 사용자가 그 명령을 직접 돌려 본 날짜와 본 것
- 볼 사람: 첫 화면 30초는 채용 담당자(비전공), 그 아래 검증 기록은 현업 엔지니어.
- 첫 화면 30초에 전할 것: 한 줄 주장, 숫자 하나(같은 파일에서 구간만 바꾸면 이동도가 몇 배 달라지는가), 그림 하나(구간별 이동도).

## 4. 계산 방법

수업 자료(8주차.pdf 9쪽)의 포화 영역 식을 그대로 쓴다.

```
I = μ · C · (W / 2L) · (V − Vth)²        ← 포화 영역에서 전류와 전압의 관계
√|I| = a · V + b                          ← 양변에 제곱근을 씌우면 직선이 된다
μ   = 2 · L · a² / (C · W)                ← 직선의 기울기 a에서 이동도
Vth = −b / a                              ← 직선이 전압 축과 만나는 점
```

- 직선을 맞추는 전압 범위가 **피팅 구간**이다. 수업 자료에는 구간을 고르는 기준이 없고 예시 `startvg=15`, `endvg=20` 하나만 있다.
- 이 도구는 "가장 좋은 구간"을 고르지 않는다. **미리 정한 구간들**에서 각각 계산해 값이 얼마나 달라지는지를 보여 준다.
  - 겹치지 않는 2 V 구간 전부 (구동 전압 크기 기준 0~2, 2~4, …)
  - 수업 예시 구간 15~20 V
  - 기존 도구가 고른 구간 (비교용, "알려진 문제 있음"으로 표시)
- 직선이 얼마나 잘 맞는지(R²)는 함께 적지만 합격선으로 쓰지 않는다. 결과를 보고 기준값을 정하는 규칙은 넣지 않는다.
- 기울기가 0 이하인 구간(소자가 꺼진 구간)은 이동도를 계산하지 않고 "계산 안 함"으로 적는다. 이것은 식이 정의되지 않는 경우를 거르는 것이며 결과에 맞춘 기준이 아니다.

## 7. 작업 단계

한 번에 한 단계만 한다. 단계를 시작하기 전에 "끝났다고 볼 조건"을 2~3개 적고, 끝나면 명령과 출력을 보여 주고 멈춘다. 사용자가 그 명령을 직접 돌려 보고 이해한 뒤에 다음으로 간다.

| 단계 | 만드는 것 | 끝났다고 볼 조건 (시작할 때 다시 확정) | 뒷받침하는 이야기 대목 |
|---|---|---|---|
| 0 | git 저장소, `.gitignore`(원자료 형식 `*.DAT`, `*.JNB`, 원자료 폴더 차단), 빈 뼈대 | `git status`에 원자료가 보이지 않음. 사용자가 저장소·커밋 그림을 설명할 수 있음 | "과정의 기록" |
| 1 | `read_raw.py`: 15개 파일의 MOBILITY 섹션 읽기 | 파일마다 점 개수, 전압 범위, 음수 전류 개수를 출력. 사용자가 원자료 한 파일을 메모장으로 열어 첫 줄과 끝 줄 숫자를 직접 대조. W/L 가정 확인 | 기준표 1번, "숫자를 직접 대조했다" |
| 2 | `fit.py`: 한 구간의 μ, Vth | 손으로 답을 아는 직선 예제 테스트 통과. `IGZO2004` 5.5~9.5 V가 검수 보고서의 8.07("맞다고 확인됨": 독립 재계산과 일치했던 값)과 맞는지 출력. 사용자가 식 네 줄을 설명할 수 있음 | "AI의 계산을 다시 따졌다" |
| 3 | 구간 훑기 + `cases.py` 2·3번 | 15개 파일의 2 V 구간별 μ 표. 수업 예시 15~20 V 값. 첫 화면에 쓸 "몇 배" 숫자 확정 | 핵심 의문 "구간에 따라 달라진다", 기준표 2·3번 |
| 4 | `cases.py` 1·4·5·6번 | 항목마다 명령 한 줄과 출력. 세 가지가 붙지 않는 항목은 뺀다 | 기준표 나머지 |
| 5 | `build.py`와 사이트 | `python -m recheck build` 한 번으로 `results/`, `site/`가 다시 만들어짐. 사이트의 모든 숫자가 `results/`와 같음. 폰 너비에서 가로로 넘치지 않음 | 첫 화면 30초 |
| 6 | GitHub 레포와 Vercel 배포 | 공개 주소에서 열림. 레포에 원자료 없음. 커밋과 푸시는 사용자가 결정 | 공개 |
| 7 | README, 자소서용 문장 초안 | 사이트·README·자소서 문장의 숫자가 서로 같음. 사용자가 모든 파일을 설명할 수 있음 | 전체 |

**"완성"의 기준**

1. 기준표의 모든 항목에 사례, 명령, 직접 확인 기록이 붙어 있다.
2. 사이트의 모든 숫자가 `python -m recheck build` 한 번으로 다시 나온다.
3. 사용자가 코드의 모든 파일을 면접에서 설명할 수 있다.

## 8. 화면

- 한 페이지. 위에서부터: 이름과 내비게이션 → 한 줄 주장 → 숫자 하나와 구간별 이동도 그림 → 검수 기준표 → 항목별 상세(사례, 명령, 출력, 확인 날짜) → AI 협업 기록 요약 → 한계(가정, 모르는 것).
- 시안은 캔버스 https://claude.ai/artifact/6E31J9uJvPtuFVqP3ibSQ7 의 "첫 화면 시안" 판. 사용자가 첫 시안(흰 카드 나열)을 거절해 두 번째 시안을 올렸다. **두 번째 시안은 사용자 확인 전이다.**
- 두 번째 시안의 방향 "계측 노트": 카드 상자 없이 굵은 괘선(2px)과 가는 괘선, 여백으로 구분한다. 그림과 표에 번호를 붙이고 숫자는 고정폭 글꼴로 맞춘다.
- 색: 바탕 `#F4F5F3`, 글자 `#1C2128`, 보조 글자 `#4A5058`, 가는 괘선 `#CDD1CC`, 링크 `#14525A`, 주의·오류 의미로만 쓰는 적색 `#B3361B`.
- 글꼴: 본문과 제목 IBM Plex Sans KR, 숫자 IBM Plex Mono. (세 번째 시안에서 명조 제목을 뺐다)
- 글자 단계 다섯: 한 줄 주장 48px 굵게 / 숫자 하나 112px 적색 / 섹션 제목 28px / 본문·표 항목·그림 제목 16px / 내비·표 머리글·축·확인 상태·주석 14px.
- 괘선: 구획 경계와 표의 머리글 아래·마지막 행 아래는 글자색 1px, 내비 아래와 표의 나머지 행은 연한 1px. 모든 구획이 같은 좌우 끝을 쓴다. 막대는 `#6B726E`, 가장 큰 값만 적색.
- 확인 상태 열(144px): 지금은 빈 네모와 "[직접 확인 전]". 확인하면 네모를 청록 `#14525A`로 채우고 "직접 확인함", 둘째 줄에 날짜를 고정폭으로 적는다.
- 세 번째 시안은 taste-skill(`design-taste-frontend`) 글을 기준으로 소넷이 고쳤다. 사진, 애니메이션, 스크립트 등 그 스킬의 나머지 요구는 따르지 않았다. **사용자 확인 전이다.**
- 그래프에도 측정점이 드러나므로 원곡선 전체는 올리지 않는다. 구간별 계산값 그림과 요약표만 올린다.

## 9. git을 쓰는 방식 (그림)

```
 내 PC                                            GitHub                    Vercel
 D:\Claude code\tft-fit-recheck
 ┌───────────────┐  커밋   ┌──────────────┐  푸시  ┌──────────────┐  자동  ┌──────────┐
 │ 파일을 고친다 │ ──────▶ │ 저장소(기록) │ ─────▶ │ 공개 레포    │ ─────▶ │ 공개     │
 └───────────────┘         └──────────────┘        └──────────────┘        │ 사이트   │
   아직 기록 안 됨          내 PC에만 있음           남이 볼 수 있음        └──────────┘
```

- **커밋**: 지금 상태를 사진 찍어 내 PC의 기록에 남기는 일. 남에게는 보이지 않는다.
- **푸시**: 내 PC의 기록을 GitHub에 올리는 일. 이때부터 남이 볼 수 있다.
- 커밋과 푸시는 사용자가 결정한다. AI는 단계가 끝나면 "무엇이 바뀌었는지"를 보여 주고 기다린다.
- 단계 하나가 커밋 하나가 되게 한다. 그러면 git 기록 자체가 과정의 증거가 된다.
